# 开发日志 2026-07-07

## 本日主要工作

### 员工工作台独立进程化

将原来的 OverlayDimmer 模态弹窗改为独立子进程窗口，支持多窗口并存、跨进程状态同步、优雅关闭。

**架构**：

```
┌─────────────────────┐    命令队列(pending_commands.json)    ┌─────────────────────┐
│   主应用 (app.py)    │ ──────────────────────────────────▶ │  员工窗口子进程       │
│                     │                                      │  (employee_app.py)   │
│  轮询命令队列        │                                      │                     │
│  执行接单/提交/阻塞  │ ◀────────────────────────────────── │  发送操作命令         │
│                     │     状态快照(employee_state.json)     │                     │
│  写入状态快照        │ ──────────────────────────────────▶ │  轮询 mtime 刷新 UI  │
│                     │     关闭信号(shutdown.signal)         │                     │
│  写入关闭信号        │ ──────────────────────────────────▶ │  检测信号 → 自行 close() │
└─────────────────────┘                                      └─────────────────────┘
```

**IPC 协议**：
- **命令**（员工→主应用）：`data/pending_commands.json`，主应用每 0.5s 轮询处理，失败重试 3 次
- **状态**（主应用→员工）：`data/employee_state.json`（PersistenceService.save() 同步写入），员工每 1s 检测 mtime
- **关闭**（主应用→员工）：`data/shutdown.signal`，员工每 0.25s 检测，检测到后自行 `close()`

## 本日踩坑

### 跨进程文件锁竞争

| 坑 | 现象 | 解决 |
|----|------|------|
| 主应用和员工窗口同时读写同一 JSON | 状态丢失/数据损坏 | `filelock` 保护主应用侧读写，员工侧只读 employee_state.json 不直接碰 board_state.json |
| `filelock` 默认阻塞无限等待 | 一方僵死另一方也卡住 | 设 `timeout=5.0` + `FileLockTimeout` 异常处理 |
| 锁粒度过大导致 UI 卡顿 | 保存 1s+ 延迟 | `poll_interval=0.1` 减少锁争用等待 |

### 进程管理

| 坑 | 现象 | 解决 |
|----|------|------|
| `proc.terminate()` / `proc.kill()` 不关 Flet 窗口 | 员工窗口仅内容消失，框架残留 | 不用杀进程——信号文件通知员工自行 `close()` |
| `os._exit(0)` 导致窗口孤儿 | Python 进程死，Flet 子进程(fletd.exe) 存活 | 同上，员工自己调 `close()` 正常退出 |
| `taskkill /F /T /PID` 杀进程树 | 同上，不一定覆盖 fletd.exe | 同上 |

### Flet 窗口关闭

| 坑 | 现象 | 解决 |
|----|------|------|
| `prevent_close=True` 关闭慢 | 点 X 后数秒窗口才消失 | **移除 `prevent_close`**，走 Flet 原生快速关闭通道 |
| 后台线程调 `destroy()` | 只清内容不关窗口 | 改用 `close()`（底层 `PostMessage(WM_CLOSE)` 线程安全） |
| `page.window.close()` 不触发 `on_close` | 自定义关闭按钮时清理逻辑未执行 | 在 `_close_window` 中显式调用 `kill_employee_processes()`，双路径覆盖 |

### 状态同步

| 坑 | 现象 | 解决 |
|----|------|------|
| 员工操作后主应用看板不刷新 | 命令队列写入后只调了 save，没调 refresh_board | `process_pending_commands` 返回后调用 `board_page._refresh_board()` |
| `PersistenceService.save()` 和 `write_employee_state()` 不同步 | 员工看到的 task 比主应用多/少 | save() 内部统一调用 `write_employee_state()` |
| 员工窗口初始数据为空 | 启动时读了空的 employee_state.json | 初始化时先用 `persistence_service.load()` 读 board_state.json 兜底 |

### 命令队列容错

| 坑 | 现象 | 解决 |
|----|------|------|
| 命令执行失败后静默丢弃 | 用户以为操作成功但没生效 | `_error` 字段记录 + `_retries` 计数，3 次内重试 |
| 队列文件并发写入冲突 | JSON 损坏 | 主应用侧串行处理（单线程轮询），不需要额外锁 |

### 联动关闭

**最终方案**：信号文件通知 + 员工自行 `close()`。

```
主应用关闭 → write_shutdown_signal() ──────────────┐
                                                    │
员工 StateSync [每 0.25s 轮询]                       │
  └─ 检测到信号 → _do_close()                        │
       ├─ stop_polling()                             │
       └─ page.window.close()  ← 原生快速关闭        │
                                                    │
主应用 page.window.close()     ← 同时原生关闭        │
```

**为什么能解决**：

1. **不走 `prevent_close=True`**——去掉后 Flet 走原生关闭通道，恢复之前的秒关速度
2. **不杀进程、不发 WM_CLOSE**——员工自己检测信号、自己调 `close()`，不依赖 PID/窗口句柄/进程树，跨平台安全
3. **`close()` 在任意线程安全**——底层是 `PostMessage(WM_CLOSE)`，不要求主线程，所以 StateSync 后台线程可以直接调
4. **主应用不等待员工响应**——写信号后立即 `close()` 自己，两边同时关，不互相阻塞
5. **信号文件残留清理**——`StateSync.start_polling()` 启动时自动删除上次残留的信号文件

### 操作后同步优化

**方案**：乐观更新——`send_command` 后立即改本地 state + refresh，不等主应用处理。

- **接单**：`state.move_task("in_progress")` + 设 `planned_start`
- **阻塞**：`state.update_task(is_blocked=True)` + `state.move_task("parts_hold")`
- **提交验收**：`state.update_task(...)` + `state.move_task("inspection")`

命令若被主应用拒绝，后台 StateSync 轮询(1s)从权威数据源自动纠正 UI。
